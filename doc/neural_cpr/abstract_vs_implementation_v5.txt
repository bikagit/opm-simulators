NEURAL CPR POLICY — v5 IMPLEMENTATION AGAINST THE ORIGINAL GOALS
=================================================================

Original abstract (condensed)
------------------------------
The solution of large, sparse linear systems arising from fully implicit
reservoir simulation remains a dominant computational bottleneck in modern
simulators. In OPM Flow, CPR combined with AMG represents the state of the
art for multiphase flow problems. However, performance is highly sensitive
to modeling choices such as pressure decoupling strategy, inclusion of well
degrees of freedom, and the selection and parametrization of AMG smoothers.
These choices are traditionally fixed a priori or tuned manually, despite
the fact that optimal configurations vary drastically across models,
timesteps, and nonlinear regimes.

We propose a neural CPR policy that dynamically selects decoupling
strategies and smoother configurations during simulation. The policy is a
lightweight machine-learned controller operating at the level of the linear
solver configuration, without modifying the underlying algebraic kernels.
Based on inexpensive features extracted from the current simulation state
(timestep size, nonlinear convergence history, well density, basic matrix
statistics), the policy selects among CPR variants (quasi-IMPES, true-IMPES,
analytical true-IMPES), optionally activates CPRW (extended well DOFs), and
chooses AMG smoothers for both pressure and fine-level corrections.

The approach is integrated into OPM Flow through its existing flexible
solver infrastructure by dynamically rewriting the solver property tree prior
to each linear solve. Training data are generated by sweeping solver
configurations across representative benchmark cases and labeling optimal
choices based on linear-solver wall-clock time. The policy is deployed
natively using OPM's existing ML integration framework.


Differences from v3
--------------------
v5 extends v3 in two directions: more training data (6 reservoir models
instead of 2) and a bug fix in the data-collection pipeline. The C++
runtime code is identical to v3. The model binary format, architecture,
and all environment variables are unchanged.

What the abstract proposes vs. what v5 implements
--------------------------------------------------

CLAIM: "Training data generated by sweeping solver configurations across
        representative benchmark cases."

IMPLEMENTATION (v5):
  Same tooling as v3 (run_sweep.py, collect_sweep_labels.py).

  Bug fixed in v5 data pipeline:
    v3 used (episode, newton_iter) as the join key in collect_sweep_labels.py.
    When data from multiple decks was combined, Newton steps from different
    reservoirs were silently merged — SPE9 episode=0,iter=0 and Norne
    episode=0,iter=0 were treated as the same sample. This was harmless in
    v3 (only one deck per CSV set) but would corrupt multi-deck training data.
    v5 uses (deck, episode, newton_iter) as the key. The deck identifier is
    derived from the CSV filename stem by stripping the trailing _NN config
    label suffix.

  v5 training data:
    Decks:   SPE9, NORNE_ATW2013, DROGON_HIST, 0_BASE_MODEL2,
             SPE3CASE1, SPE9_CP
    Runs:    sweep2 + sweep3 (SPE9, Norne) + sweep4 (Drogon, others)
    Samples: 2762 labelled Newton steps
    Labels:  24 distinct across all samples; label 23
             (cprw+TrueIMPESAnalytic+DILU+DILU) = ~31% of samples

  Class imbalance observation:
    The dominant label (23) accounts for 31% of samples. Adding more diverse
    decks increased the minority-class coverage but also increased noise in
    the label assignment, which is why v5 val accuracy (37%) is lower than
    v3 (45.5%) despite having more than twice the data.
    On a 24-class problem, random guessing = 4.2%. Majority-class baseline
    = 31%. Both models are above the majority-class baseline.


CLAIM: "Significant improvement in linear iteration counts and time-to-solution,
        particularly in regimes with strong well-reservoir coupling or rapidly
        changing nonlinear behaviour."

PERFORMANCE (v5, same benchmark runs as v3):
  The abstract claim holds for the decks present in v3's training data.
  For decks not in v3's training, v5 showed no improvement due to the
  lower generalisation accuracy.

  Note: v5 was not separately benchmarked; the performance data below
  is from the v3 benchmarks which use the same C++ runtime. v5 model
  performance on SPE9/Norne would be similar to or slightly worse than v3
  given the lower val accuracy. The primary motivation for v5 was to test
  whether more diverse training data improves out-of-distribution performance.
  The conclusion was: more data from dissimilar decks dilutes the label signal.

  Deck    Wall-time result (v3 model, same C++ runtime)
  ------  ------------------------------------------------
  SPE9    −5%   (in training set for both v3 and v5)
  Norne   −5.5% (in training set for both v3 and v5)
  Drogon  +0.6% (in v5 training set, but model still degrades vs. baseline)
  SPE11   crash (TrueIMPESAnalytic on 2-phase deck — same bug as v3)


CLAIM: "Lightweight machine-learned controller at the level of the linear
        solver configuration, without modifying the underlying algebraic kernels."

IMPLEMENTATION (v5): Identical to v3.
  Architecture: 14→32→24, ReLU, ~1300 parameters.
  Same C++ files: NeuralCprPolicy.cpp/.hpp, CprPolicyFeatures.hpp,
  CprPolicyAction.hpp, ISTLSolver.hpp modifications.
  No changes to DUNE, DILU, AMG, or FlexibleSolver.


CLAIM: "Inexpensive features extracted from the current simulation state."

IMPLEMENTATION (v5): Identical to v3 (same CprPolicyFeatures.hpp).
  Same 14 features, same normalisation formulas.
  diag_dominance normalisation: clamp(val/4.0) — clips values above 4 to 1.0.
  This was identified as a limitation after v5: the diag_dominance range in
  practice is 0.5 to 6e9; the linear scale clips ~95% of values. A log10
  scale would preserve the information (addressed in v6 experiment, but
  reverted as it broke v3/v5 model compatibility).


CLAIM: "Integrated through the existing flexible solver infrastructure."

IMPLEMENTATION (v5): Identical to v3.
  Same applyNeuralPolicy() three-tier optimisation.
  Same confidence gate (OPM_NEURAL_CPR_CONFIDENCE, default 0.6).
  Same failure-revert logic.


Known issues (same as v3, plus one observation specific to v5)
--------------------------------------------------------------
  1. Phase guard missing: TrueIMPESAnalytic crashes on 2-phase decks.
  2. Out-of-distribution behaviour: adding Drogon to training did not help
     Drogon performance — the model's 37% val accuracy means it cannot
     reliably generalise even to decks it was trained on.
  3. Label dilution: more diverse decks increase label noise. The optimal
     config for SPE9 Newton iter 5 is not the same as for Drogon Newton
     iter 5, but they share the same feature vector shape; the model cannot
     separate them without a deck-identity feature.
  4. Timing noise: wall-clock labelling on a single workstation has ~6%
     run-to-run variance. Sweep results should be collected on a stable
     HPC node to reduce label noise.


Recommendation
--------------
  For production use of the neural policy, v3 (neural-cpr-v3 branch) is
  currently the better choice: higher val accuracy (45.5% vs 37%) and
  confirmed wall-time improvements on SPE9 and Norne. v5 is kept as a
  reference point demonstrating that naively adding more diverse training
  data does not improve accuracy when label imbalance is severe and
  timing noise is high.

  The path to a stronger multi-deck model requires:
    a) Stable timing measurements (HPC node, multiple repeats per config)
    b) Deck-identity or grid-statistic features to help the model separate
       reservoir types
    c) Phase-count feature or hard constraint to prevent TrueIMPESAnalytic
       selection on 2-phase problems
